# Как составлять структурную схему (Э1) и требования к блокам

Методичка для агента-дизайнера, контролёра требований и критика.
Содержание универсально: данных конкретного устройства здесь нет.

**Нормативная база** (цитаты и номера пунктов — см.
`docs/reference/gost_structural_scheme.md`):
- ГОСТ 2.701-2008 / ДСТУ ГОСТ 2.701-2013 — виды и типы схем;
- ГОСТ 2.702-2013 / ДСТУ ГОСТ 2.702-2013, п. 5.1 — правила выполнения
  структурных схем (один и тот же текст ЕСКД);

- ГОСТ 2.710-81 / ДСТУ ГОСТ 2.710-2012 — буквенно-цифровые обозначения
  элементов, устройств и функциональных групп;

- ГОСТ 2.709-90 / ДСТУ ГОСТ 2.709 — обозначения цепей (предмет
  Э2/Э3, на Э1 не применяются: п. 4.5 ЕСКД допускает поясняющие надписи,
  которые подписываются назначением, а не именем цепи).

## 1. Что такое Э1 и чего на ней нет

ГОСТ 2.701: Э1 отображает принцип работы изделия в самом общем виде.
ГОСТ 2.702 п. 5.1.1: «На структурной схеме изображают все **основные
функциональные части** изделия (элементы, устройства и функциональные
группы) и **основные взаимосвязи** между ними».

Отсюда — что на Э1 **нельзя** (и за это каркас рубит спецификацию):

- **позиционные обозначения деталей** (`R1`, `U3`, `LED2`): они
  принадлежат принципиальной схеме — ГОСТ 2.702 п. 5.3.7, 5.2.15. На Э1
  функциональная часть безымянна и описывается наименованием;
- **номиналы и выводы**: «10 мкФ», «вывод 3» — только на Э3;
- **имена электрических цепей** (`VREG`, `LED_KAT`, `+3V3`): это
  обозначения цепей по ГОСТ 2.709, они ставятся на схемах, где видны
  выводы. Линия Э1 — это **взаимосвязь**, и подписывается назначением
  сигнала, а не именем цепи;
- **сети питания и земля как линии**: они не являются связью между
  функциональными частями и на Э1 не рисуются.

Можно и нужно (ГОСТ 2.702 п. 4.5 — допускаются поясняющие надписи):
наименование части, назначение сигнала на линии, стрелки направления
процессов (п. 5.1.3 — рекомендуется).

## 2. Разбиение на блоки

1. **Деление по функции, а не по конструкции** (п. 5.1.1). Блок —
   функциональная часть с одной понятной ролью: «усиление»,
   «преобразование питания», «управление». Деталь входит в блок по своей
   роли в изделии.
2. **Блок — прямоугольник с наименованием внутри** (п. 5.1.2 и 5.1.4:
   «наименования каждой функциональной части… должны быть указаны»).
   В прямоугольнике две строки: `КОД — НАИМЕНОВАНИЕ` и назначение.
3. **Код — буква функции по ГОСТ 2.710, а не первая буква детали.**
   J1 в блоке питания — это функциональная часть `G1`, а не разъём.
   | Функция | Код | | Функция | Код |
   |---|---|---|---|---|
   | Источник питания, генератор, батарея, заряд | **G** | | Измерительный прибор | **P** |
   | Усилитель, стабилизатор, регулятор, устройство | **A** | | Антенна, СВЧ-тракт | **W** |
   | Преобразователь величин, модулятор/демодулятор, выпрямитель | **U** | | Разъём, соединитель | **X** |
   | Интегральная схема, процессор, память | **D** | | Индикация, сигнализация, свет/звук | **H** |
   | Датчик, преобразователь неэлектрических величин | **B** | | Фильтр, ограничитель, линия задержки | **Z** |
   | Защита, предохранитель, разрядник | **F** | | Реле, контактор | **K** |
   | Коммутация, переключение, управление | **S** | | Трансформатор, дроссель | **T** |

   Номера — по порядку следования частей в схеме (`G1`, `G2`, `A1`).
   Неиспользованный код не подставляют: если части по смыслу нет в
   таблице, берут ближайший по роли.
4. **Покрытие без дыр:** каждый компонент входит ровно в один блок; блок
   определяет, где компонент *выполняет* свою роль, даже если деталь
   участвует и в другой функции.
5. **Порядок блоков = ход сигнала** (п. 5.1.3, стрелки направления
   процессов): источник → потребитель, слева направо.
6. **Источник и сток видны явно**: часть, которая только выдаёт
   (источник питания, излучатель) или только принимает (антенна, датчик),
   остаётся блоком со своими интерфейсами.
7. **Много блоков — не повод отказываться от наименований** (п. 5.1.5):
   если частей больше десятка, коды `1, 2, 3…` и таблица на поле схемы
   допустимы, но прямоугольник с наименованием всегда понятнее; в
   спецификации `title` обязателен в любом случае.

## 3. Как выглядит блок по классам изделий

Ориентир по назначению, а не по копированию: состав блоков выводится
из заказа, примеры показывают лишь типовой разбор.

| Класс изделия | Типовой ряд блоков (пример) |
|---|---|
| Усилитель/приёмник сигнала | Антенна (W) → УС (A) → Смеситель/детектор (U/A) → УПТ (A) → Демодулятор (U) → Выход (A) |
| Источник питания | Вход (X) → Защита (F) → Преобразователь (U/G) → Стабилизатор (A) → Выход, Индикация (H) |
| Измерительный прибор | Датчик (B) → Усилитель (A) → Преобразователь (U) → Вычислитель (D) → Индикация (H) |
| Управляющее устройство | Вход/датчики (B) → Логика (D) → Коммутация/исполнительные (S/Y) → Индикация (H) |
| Осветитель/источник света | Источник питания (G) → Преобразователь (U) → Источник света (E) → Управление (S) → Индикация (H) |
| Система сбора/телеметрии | Объект/датчики (B) → Нормализатор (A) → Оцифровка (D) → Передача/связь (U) |

## 4. Требования к блоку (что писать)

Формулируются **измеримые** требования из ТЗ и расчётов:

- **назначение**: одна фраза — что блок делает;
- **вход/выход**: какие сигналы и в каком направлении;
- **бюджеты**: питание, потребление, допуски;
- **точность/диапазон**: по результатам расчётов;
- **способ проверки**: что и чем измеряется (критерий приёмки).

Плохо — «блок питания». Хорошо — «БЛОК ПИТАНИЯ: вход 12 В ±10 %,
стабилизированная шина 5 В ±2 %, ток до 1 А, защита от КЗ, проверка —
измерение Uвых под нагрузкой».

## 5. Проектирование узла и режим сборки

Блок — не «общее место»: топология строится без детализации, но каждый
функциональный узел **сразу получает собственное схемотехническое
решение**: типовую схему включения из первоисточника (даташит выбранной
детали, аппнота производителя, книга из `knowledge/electronics_sources.md`)
и точные номиналы из расчёта. В спецификации это поля блока `params`
(числовые требования) и `refs` (какие детали образуют узел). Числа не
выдумываются: или расчёт (`design/calc.json`), или значение из даташита
реальной детали — со ссылкой на источник.

**Режим сборки** задаёт заказ, фиксирует консультант (поле
`можно_модули` в `design/acceptance.json`):

- `true` — модули допустимы, только если паспортные параметры модуля
  покрывают требования блока. Реальный модуль (например, плата зарядки
  на TP4056) агент находит сам или поиском в каталоге поставщика
  (инструмент `part_search`); обязательны реальный SKU и документ.
  Нет подходящего модуля — узел считается сам из компонентов;
- `false` — «всё собираем сами»: готовых плат и модулей нет, каждый
  узел проектируется **своим циклом разработки**:
  1. топология — из первоисточника (типовая схема включения);
  2. расчёт — все номиналы по формулам, с допусками;
  3. подбор — реальные компоненты с даташитами (каталог `part_search`,
     библиотекарь);
  4. схема — спецификация узла и нетлист (поблочный SKiDL);
  5. проверка — симуляция (SPICE) и сторожевые проверки узла;
  6. правка — цикл повторяется, пока критерии узла не выполнены.

Каждый блок собирается отдельным прибором SKiDL: выводы — из реальных
символов, внутренние сети — из спецификации, наружу — клеммы. Нетлист
блока (`design/blocks/*.net`) сверяется со спецификацией; расхождение
блокирует сшивание схемы и возвращается дизайнеру. Инструмент:
`python3 tools/skidl_blocks.py --project .` (`--check` — только
проверки). Движок ничего не подсказывает: он проверяет ровно то, что
выводы существуют в реальных символах и каждый стоит в одной сети.

## 6. Чек-лист перед сдачей

- [ ] Каждый блок: код + наименование + назначение + интерфейсы
- [ ] У каждого функционального блока — своё решение: типовая схема
      включения из первоисточника, номиналы — из расчётов (`params`)
- [ ] Числа в блоках — только с источником (расчёт/даташит); «на глаз»
      ничего не вписано
- [ ] В режиме «всё сами» (`можно_модули`=false) готовых модулей нет
- [ ] Ни одного ref детали и ни одного номинала в блоках
- [ ] Ни одного имени цепи в подписях линий; сети питания не нарисованы
- [ ] Каждый компонент ровно в одном блоке, пустых блоков нет
- [ ] Блоки идут по потоку сигнала, источник и сток видны
- [ ] Питание есть: в спецификации есть сети с полем `power`, и к ним
      подключены потребители
- [ ] Номиналы блоков совпадают с расчётами
- [ ] Нет блока, не связанного ни с одной сетью и без refs
