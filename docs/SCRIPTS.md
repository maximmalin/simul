# Скрипты проекта — что каждый делает

Документ описывает **все скрипты конвейера** и разделение труда
(см. также `docs/HARDWARE_AGENT_CYCLE.md` — про цикл агентов).

Главное правило архитектуры:

> **Содержание изделия пишут агенты, механику исполняют скрипты.**
> Агент решает: состав компонентов, соединения, сети питания, номиналы,
> расчёты, текст ТЗ. Скрипты: компиляция схемы, проверка, разводка,
> автороутинг, экспорт форматов. Ни один скрипт не «знает» конкретное
> устройство и не вписывает за агента ни компонент, ни номинал, ни сеть.

## 1. Конвейер заказа (одно и то же для любого устройства)

```
текст заказа
   │
   ├─ make tz        → каркас ТЗ из структуры эталона technical_task.md
   ├─ агент-расчётчик → design/calc.json
   ├─ агент-библиотекарь → design/library_index.md (реальные lib_id/пины)
   ├─ петля ТЗ        → design/technical_task.md
   │    писатель → дебагер (JSON-вердикт) → писатель → … → оптимизатор
   ├─ агент-контролёр  → design/checklist.md (критерии приёмки схемы)
   ├─ агент-дизайнер × N параллельно → design/schematic.json
   │    отбор — строгой валидацией каркаса и агентом-критиком
   ├─ make kicad     → tools/schematic_from_json.py
   │     строгая валидация спецификации (ошибки — агенту на исправление,
   │     с памятью ошибок всех попыток)
   │     → <Изделие>.kicad_sch, .net, generate_result.json (манифест)
   ├─ make spice     → НАТИВНЫЙ экспорт KiCad:
   │     kicad-cli sch export netlist --format spice  → <Изделие>.cir
   ├─ make sim       → tools/ngspice_measure.py: ngspice по деке →
   │     out/hardware/measurements.json (факты; подсхемы НЕ заменяются
   │     заглушками — модели берёт агент, см. решение в модуле)
   ├─ агент-размерщик (EEsizer-петля: замер → правка номиналов →
   │     пересборка деки → новый замер; история замеров идёт в промпт)
   ├─ make gost      → плата tscircuit + чертежи ГОСТ:
   │     run_pcb.py → resolve_parts.py (парт-номера) + build_pcb.mjs
   │     (нетлист → TSX → tsci: автороутинг + полный экспорт) → board.step
   │     gost_pipeline.py: STEP → очистка Analysis Situs → FreeCAD
   │     TechDraw → DXF/SVG/PDF
   ├─ make all       → deliverables механикой из агентских артефактов:
   │     структурная схема: блоки агента → structure.dot → рендер
   │     svg/png → ИМПОРТ в structure.drawio (геометрия от graphviz);
   │     параллельно .mmd (mermaid) и .d2 как текстовые исходники;
   │     board.svg (нативный kicad-cli), 3D (экспорт tscircuit),
   │     страница с ТЗ агентов
   └─ make test      → проверка комплектности артефактов
```

Кто за что отвечает: **состав, соединения, функциональные части, ТЗ,
расчёты, номиналы — агенты**; геометрия, экспорт, чертежи, оформление —
скрипты. Каркас не подставляет ни значений, ни моделей, ни заглушек.

Роли агентов живут файлами в `backend/agents/roles/*.md` (по образцу
промптов analog-agents), методичка структурной схемы — в
`backend/agents/knowledge/structural_scheme.md`. Эталоны методологии:
`docs/reference/analog-agents/` (роли, контракты, ревью, усилие) и
`docs/reference/eesizer/` (симуляция в петле с размерами).

## Уровни усилия и параллелизм

`KR_EFFORT=lite|standard|intensive` задаёт бюджет: сколько попыток
дизайнера, размерщика, ТЗ-петли, есть ли критик и сколько дизайнеров
работают параллельно (`KR_DESIGN_CANDIDATES`). Модели отвечают через
гонку `backend/llm_race.py`: несколько маршрутов стартуют одновременно,
побеждает первый ответ (`KR_RACE`, `KR_RACE_WIDTH`, `KR_RACE_HOLD`).
Заказ без прогресса дольше `KR_STALL_S` секунд останавливает сторож
`service.watchdog` с честным диагнозом.

## 2. Агентский слой (`backend/agents/`)

| Файл | Роль |
|---|---|
| `roles/*.md` | Ролевые карточки агентов: **консультант** (приём замысла), библиотекарь, писатель, дебагер, оптимизатор, контролёр требований, дизайнер, критик, размерщик — по образцу промптов analog-agents (Права / Входы-контракт / Выход / Критерии приёмки / Стиль) |
| `knowledge/structural_scheme.md` | Методичка составления структурной схемы и требований к блокам (ГОСТ 2.701/2.702) |
| `service.py` | Жизненный цикл заказа: анализ текста, запуск конвейера, публикация логов/SSE, **сторож заказа** (`KR_STALL_S` — объявляет зависание сам). |
| `stages.py` | Каркас конвейера: стадии `tz → calc → library → tz_write → checklist → schematic → kicad → spice → sim → sizing → gost → all → test`; петли ТЗ/критика/подгонки; память ошибок и показ прошлой попытки агенту; транскрипт `design/agents_transcript.md`. |
| `tools.py` | Инструменты агента: `write_artifact`, `run_target`, `kicad_libs` (search/pins/footprints по реальным библиотекам KiCad). |
| `engine.py` | Диспетчер, публикация состояния с метками времени, видимая ошибка публикации. |
| `llm.py` | Клиент LLM: маршруты, отметка живых/мёртвых, единичный вызов `chat_one`. |
| `llm_race.py` | Гонка маршрутов: первый ответ выигрывает, победитель идёт первым дальше (`KR_RACE`, `KR_RACE_WIDTH`, `KR_RACE_HOLD`). |
| `sandbox.py` | Песочница заказа и **политика зависимостей** (раздел 8). |

## 3. Схема: `tools/` и `hardware/kicad/`

| Скрипт | Что делает |
|---|---|
| `tools/schematic_from_json.py` | **Компилятор принципиальной схемы.** Единственный вход — JSON-спецификация агента (`design/schematic.json`). Валидирует (уникальность ref, существование символов/пинов, полнота соединений) и выдаёт machine-readable ошибки — они возвращаются агенту. Затем подменяет таблицы движка разводки, строит `.kicad_sch`, экспортирует `.net` и ERC, пишет **`generate_result.json`** — манифест для платы (netlist, stem, `power_nets`, `ground`, title). |
| `hardware/kicad/generate_brig_receiver.py` | **Движок разводки схемы.** Принципиально не привязан к схеме приёмника: его входы — таблицы `PARTS`/`NETS`/`BLOCKS` (это проверено `test_any_schematic.py`). Строит геометрию листа и пишет `.kicad_sch`. |
| `hardware/kicad/kicad_lib_brig.py` | Парсер библиотек символов KiCad: список библиотек, символов, выводов. Обслуживает инструмент агента `kicad_libs` — у агента нет другого способа узнать символы/пины. |
| `hardware/kicad/kicad_lib.py` | Хелпер генерации символов (проект SDR, не в конвейере заказа). |
| `hardware/kicad/test_any_schematic.py` | Проверка универсальности движка: прогоняет **чужую** схему через тот же pipeline — таблицы являются единственным входом. |
| `tools/ngspice_measure.py` | Замер: `.cir` → ngspice → `measurements.json`. Измеритель, а не помощник по проектированию: подсхемы **не** заменяются заглушками — модели приборов подключаются, если есть готовые библиотеки (`design/spice_models.lib`, `spice/models.lib`, KiCad `Simulation_SPICE.sp`), а неразрешённое попадает в отчёт `blocked`. Какая модель соответствует символу — решение агента. |
| `hardware/kicad/verify_nets.py` | Строгая сверка экспортированного нетлиста с таблицей `NETS`: для каждой сети точное множество `(ref, pin)`. |
| `hardware/kicad/build_board.py` | Опс-сборка платы SDR-приёмника: SKiDL → kinet2pcb → kicad-cli (герберы, 3D, BOM). Внеконвейерный скрипт исходного изделия. |

## 4. Плата: `hardware/tscircuit/`

**Футпринты и плата — забота tscircuit-конвейера**, а не ручных правил.
KiCad-нетлист → код tscircuit → официальный CLI (`tsci`) → автороутинг
и полный экспорт (kicad_pcb, step, glb, gerbers, PDF, нетлист).

| Скрипт | Что делает |
|---|---|
| `run_pcb.py` | **Универсальный раннер** (новый). Читает манифест компилятора и передаёт факты штатным скриптам: `--netlist`, `--manifest`, `OUT_DIR`; о нет готовой заготовки — честный пропуск с сообщением (никогда не устанавливает). |
| `build_pcb.mjs` | **Эмиттер TSX.** Разбирает нетлист KiCad (любой версии), эмитит `<chip>` с явными `pinLabels` — полярность исключена по построению (`REF.pinN`). Сети питания и заливки — из **манифеста** (`power_nets`/`ground` решены агентом); манифеста нет — общий фолбэк по электротехнической фонетике имени (GND/VSS-семейство, VIN/VBUS/VBAT/VCC/VDD, напряжения вида `+3V3`). Параметры: `NETLIST`, `OUT_DIR`, `MANIFEST`, `BOARD_W/H`, `KICAD_FP_ROOT`, `KICAD_MODELS_ROOT`, `ROUTING_ONLY`, `PCB_3D`/`--full`. |
| `resolve_parts.py` | **Подбор парт-номеров** по локальной базе JLCPCB (`jlcsearch.db`): тип детали — из библиотеки корпуса, номинал — из поля Value, пакет — из корпуса KiCad. Параметры: `--netlist`, `--out`, `--db`, `--models`. База собирается один раз (`build_derived.py`), в цикле заказа не пересобирается. |
| `build_derived.py` | Подготовка базы деталей в стиле jlcsearch из `cache.sqlite3` (jlcparts): числовые колонки с теми же именами, что у tscircuit-движка. **Заготовка, собирается один раз.** |
| `fetch_3dmodels.sh`, `fetch_3dmodels_fallback.sh`, `fetch_vendor_models.mjs` | Заготовка зеркала 3D-моделей (packages3d/pcb-3d, оффлайн). Зеркало приводится к STL. |
| `step2stl.py` | Пакетная конвертация STEP → STL: tscircuit инлайнит только известные форматы (glb/gltf/obj/stl), `.step` теряется в экспорте. **Заготовка.** |
| `check_models3d.py` | Проверка посадки 3D-моделей: детали должны стоять по центру компонента без сдвигов. |
| `site_assets.py` | Перенос 3D-моделей в статику сайта `dist/` (circuit.json с локальными путями → 404 на сайте без переноса). |
| `make_viewer.py` | Сервер 3D-просмотра платы (DXF + GLTF). |
| `check_net.py` | Факт-проверка, что страница просмотра не ходит в сеть: поднимает сервер, запускает headless Chrome, читает сетевой лог. |
| `viewer/` | Сборка сайта tscircuit (rollup). |

## 3а. Кто и что решает в заказе

Роли идут от замысла к изделию; каждая имеет **право решения**, а не
только право проверки:

| Роль | Что решает | Артефакт |
|---|---|---|
| **Консультант** (приём замысла) | нужны ли расчёты физики и какие именно; **нужен ли микроконтроллер**; функциональные части; допущения | `design/acceptance.json` |
| Расчётчик | величины и формулы по решению консультанта | `design/calc.json` |
| Библиотекарь | какие реальные символы/пины/корпуса доступны | `design/library_index.md` |
| Писатель → дебагер → оптимизатор | документ ТЗ | `design/technical_task.md` |
| Контролёр требований | критерии приёмки схемы | `design/checklist.md` |
| Дизайнер (×N параллельно) | состав, соединения, функциональные блоки | `design/schematic.json` |
| Критик | рубит спецификацию до компиляции, ничего не правит | вердикт в лог |
| Размерщик (EEsizer-петля) | номиналы по фактам замера | патчи в `design/schematic.json` |

**Порог по умолчанию — никакой избыточности, но заказ — закон.**
Сначала заказ читается буквально: если в тексте прямо назван
микроконтроллер, МК, SoC, Raspberry/Pi/Arduino/ESP/STM32 или ПЛК —
это требование заказчика, и консультант регистрирует «нужен», а не
спорит. Если не сказано — порог «нет»: управление режимами и
яркостью, защита, зарядка, таймеры и автоотключение решаются схемой;
программируемый элемент вводится только при невыразимом схемой
(память между включениями, протоколы обмена, алгоритмы с ветвлением,
измерение и обработка сигнала).

Отдельно решается **тракт обработки сигнала** (GNU Radio, машинное
обучение, FPGA) — это заметка о составе изделия, а не о
микропрограмме. Порог тот же: фильтр, усиление, детектирование и
пороги делаются схемой; заметка «нужен» ставится, только когда из
заказа прямо следует программная обработка в реальном времени на
рабочей станции, обучение моделей или ПЛИС-логика.

Каркас проверяет полноту решения: пустое поле (`нужен_тракт_обработки`
не заполнено) или «да» без обоснования означает, что вопрос **не
решён**, а не «нет».

## 4а. Два разных документа: Э1 и принципиальная

Их часто путают — поэтому правило зафиксировано явно:

| | **Структурная схема (Э1)** | **Принципиальная схема** |
|---|---|---|
| Отвечает на вопрос | «из чего по назначению состоит изделие, как проходит сигнал» | «как соединены конкретные выводы» |
| В прямоугольнике | функция и её назначение: `A1 ПИТАНИЕ`, `H1 ИНДИКАЦИЯ` | УГО детали: символ, пины, позиционное обозначение |
| Обозначения | буквенные коды **функций** (ГОСТ 2.739): A, H, K, Z, G, B | буквенные коды **элементов**: R, C, U, D, L, J |
| Номиналы, полярность | **нет** | **да** |
| Имена цепей (VREG, LED_KAT) | **нет** — на линии назначение сигнала | **да**, с номерами выводов |
| Пины подключения | **нет** | **да** |
| Сети питания и земля | **не изображаются** | изображаются со символами питания |
| Кто делает | агент задаёт функциональные части (`blocks`), механика оформляет | спецификация агента → компилятор → `.kicad_sch` |

Именно поэтому подпись линии Э1 переводится из имени цепи в назначение
сигнала (`питание`, `управление`, `данные`, `индикация`), а обозначения
блоков считаются по функции, а не по первой букве ref детали.

## 6. Заготовки (подготовка зависимостей — один раз)

Политика: **конвейер заказа ничего не устанавливает и не пересобирает.**
Всё тяжёлое готовится заранее операционно (по этой таблице) и живёт в
репозитории; заказ только *берёт* готовое — `sandbox.py` копирует
заготовки в песочницу (`SHARED_DIRS`, `DEPS_CACHE`), а `run_pcb.py` и
`resolve_parts.py` честно сообщают, если заготовки нет.

| Заготовка | Как готовится (один раз) | Кем берётся |
|---|---|---|
| `.venv` (Python-KiCad-SKiDL) | стандартная установка окружения | make-цели, компилятор схемы |
| `node_modules` с `@tscircuit/cli` (`tsci`) | `npm install` в корне | `build_pcb.mjs` (`npx --no-install tsci` — сеть не нужна) |
| `hardware/tscircuit/out/jlcsearch.db` | `build_derived.py` | `resolve_parts.py` |
| `hardware/tscircuit/models/` (STL-зеркало) | `fetch_3dmodels.sh` → `step2stl.py` | `build_pcb.mjs` (3D-экспорт), `resolve_parts.py` |
| `/usr/share/kicad/{symbols,footprints}` | установленный KiCad | библиотеки символов/вывод/"выводы"/корпусов |
| `dot` (graphviz) | системный пакет | оффлайн-рендер структурной схемы в SVG/PNG |
| `d2` (опционально) | готовый бинарь terrastruct | рендер `structure.d2`; без него лежит исходник |
| `mmdc` (опционально) | `@mermaid-js/mermaid-cli` в node_modules | рендер `structure.mmd` |

Признак отсутствия заготовки — **внятная строка в логе и пропуск шага с
сохранением остального потока данных** (плата уходит без парт-номеров
или в режиме `ROUTING_ONLY`), а не сетевая установка внутри заказа.

## 7. Параметры универсализации платы

| Переменная | Смысл |
|---|---|
| `NETLIST` | нетлист KiCad конкретного изделия |
| `MANIFEST` | `generate_result.json` (сети питания агента, ground, title) |
| `OUT_DIR` | каталог сборки платы (в заказе — `out/hardware/tscircuit`) |
| `BOARD_W`, `BOARD_H` | габарит платы; по умолчанию авто-подбор под компоненты |
| `ROUTING_ONLY` | быстрый прогон (только circuit.json) |
| `AUTOROUTER_EFFORT` | усилия авроутера (умолчание `10x`) |
| `KICAD_FP_ROOT`, `KICAD_MODELS_ROOT` | свои библиотеки корпусов и зеркало моделей |
| `KR_DEPS_3D` | копировать тяжёлое 3D-зеркало в песочницу заказа |
| `KR_SANDBOX_LINKS` | жёсткие ссылки зависимостей вместо копии (экономит ГБ) |

## Честный каркас (правила, по которым пишется код)

1. **Агент решает, каркас проверяет.** Никакой «ремонт» решения
   агента, если только это не очевидная механика (повтор (ref, pin) в
   двух сетях, orphan-компонент). Хирургический ремонт допускается и
   логгируется («хирургическая правка») — он делает только то, что нет
   смысла требовать от модели.
2. **Обрезка артефактов честная.** Карточка роли, методичка и
   артефакты заказа режутся по границам разделов; если не уложилось —
   в конец дописывается список отброшенных разделов. Китающих символов и
   обрывов на полуслове нет.
3. **Никакого хардкода сказать недостаточно — проверено CODE_AUDIT.md.**
   Оставшиеся упоминания «Krystal Radio» — только докстринги и дефолты
   ручного запуска, в заказе не используемые.
4. **Логирование** — каждый ход агента с меткой времени (HH:MM:SS) в
   `work/orders/<id>/logs/live.log`, на фронтенде — живая консоль.
5. **Решение консультанта** (нужен ли микроконтроллер, нужен ли тракт
   обработки сигнала) доходит дословно до расчётчика, писателя ТЗ,
   контролёра требований и дизайнера schematic.json.
